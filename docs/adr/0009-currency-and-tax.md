# ADR-0009: Multi-currency from day one, Stripe Tax for compliance, Stripe-generated invoice numbers

- **Status:** Accepted
- **Date:** 2026-05-26
- **Deciders:** Markus

## Context

The integrating apps may sell globally from day one (EU + US + UK + further markets). The lib must support:

- Multiple presentment currencies (a customer in the US sees USD; a customer in Austria sees EUR).
- Compliant tax handling across many jurisdictions (Austrian VAT, EU reverse-charge for B2B, OSS for EU B2C, US sales tax where nexus applies, UK VAT post-Brexit, etc.).
- Multiple payment methods reflecting B2B EU norms (cards, SEPA Direct Debit, Apple Pay, Google Pay, bank transfer).
- Invoice generation that satisfies Austrian §11 UStG and equivalents.

Getting tax wrong is not a code bug — it's a legal/financial liability with the Finanzamt and equivalent authorities elsewhere. This ADR locks in the strategy that minimizes that exposure.

## Decision

### Currency: multi-currency, app-declared per Price

The catalog supports N currencies per Product. Each `Product` may have multiple `Price` entries that differ in currency:

```go
"pro_plan": Product{
    Prices: map[string]Price{
        "monthly_eur": {Amount: 4900,  Currency: "eur", Interval: "month"},
        "monthly_usd": {Amount: 5400,  Currency: "usd", Interval: "month"},
        "monthly_gbp": {Amount: 4200,  Currency: "gbp", Interval: "month"},
        "yearly_eur":  {Amount: 49000, Currency: "eur", Interval: "year"},
        "yearly_usd":  {Amount: 54000, Currency: "usd", Interval: "year"},
        "yearly_gbp":  {Amount: 42000, Currency: "gbp", Interval: "year"},
    },
}
```

The app picks the currency at checkout time, either by passing the explicit lookup_key (`pro_plan.monthly_usd`) or by passing a currency hint and letting the lib resolve to the matching Price for the requested interval. Stripe Checkout's locale detection is used to *display* localized prices on the hosted page, but the chosen currency is determined by the app's choice, not by the buyer's IP.

Settlement currency (what hits your bank) is configured in Stripe (typically EUR for an Austrian business); Stripe converts non-EUR presentment to EUR at its FX rate at settlement time, deducting a 1% FX fee. This is acceptable and documented.

**Initial currencies for phase 0:** EUR, USD, GBP. Adding more is one entry per Product in the catalog — no code changes.

### Tax: Stripe Tax (Approach A) — automated, paid

The lib enables `automatic_tax: { enabled: true }` on every Checkout Session, Subscription, and Invoice it creates. Stripe Tax:

- Calculates the correct VAT/sales tax based on buyer location and product type.
- Validates VAT IDs against the EU VIES system automatically; reverse-charge is applied when validation succeeds, full VAT charged when it fails or no ID is provided.
- Generates invoice text that complies with EU/Austrian requirements (reverse-charge note, VAT breakdown, customer VAT ID line).
- Handles US sales tax where the merchant has registered nexus, UK VAT, and OSS reporting data for EU B2C.

**Cost:** 0.5% per transaction where tax is calculated, capped at $0.50 USD per transaction. Treated as a cost of compliance — cheaper than tax-software subscriptions plus the risk of getting reverse-charge wrong.

**B2B VAT ID collection is mandatory** on every checkout. The lib's Checkout API sets `tax_id_collection: { enabled: true }` and `customer_update: { name: 'auto', address: 'auto' }` by default — buyer must supply a billing address; B2B buyers can supply a VAT ID for reverse-charge.

**Tax filing is NOT in scope** for Stripe Tax or this lib. Monthly UVA (Umsatzsteuervoranmeldung) and quarterly OSS returns are filed by the user / their tax advisor using Stripe Tax's exported reports.

### Invoices: Stripe generates them; lib provides audit-log helper

Invoice numbers are generated by Stripe (e.g. `INV-A0001-0001`). Austrian §11 UStG requires sequential gapless numbering; Stripe's numbering is sequential within a prefix but can have gaps when invoices are voided before finalization. This is accepted, with two mitigations:

1. **Audit log helper:** the lib exposes `conn.Invoices.ExportAuditLog(period)` that pulls Stripe's invoice + event history for a period and produces a CSV/JSON suitable for handing to a tax advisor or the Finanzamt, documenting any number gaps with their cause.
2. **Override mechanism designed in but unused for phase 0:** the `Invoices.Create` API in the lib accepts an optional `NumberOverride string`. Apps that later want to own numbering can implement an invoice-number repo and pass values in. Switching from "trust Stripe" to "own the numbering" requires no breaking changes — just start passing the override.

### Payment methods: cards + SEPA Direct Debit + Apple/Google Pay + bank transfer

The lib's default Checkout Session enables all four for B2B-suitable use cases. Stripe's Payment Method Configuration handles availability per region (e.g. SEPA only shown for EU buyers, ACH for US buyers — not enabled day one but designed in).

Mapping per use case:

| Use case | Methods enabled |
|---|---|
| One-time purchase | card, apple_pay, google_pay, sepa_debit (EU only) |
| Subscription | card, sepa_debit (preferred for EU recurring), apple_pay, google_pay |
| Invoice (net-30, manual) | customer_balance / bank_transfer + card fallback |
| Credit pack top-up | card, apple_pay, google_pay |

**Phase 0 default:** Stripe Checkout Sessions (hosted page) — Stripe owns the UI; lib just creates the session. This eliminates entire categories of bugs (PCI scope, payment-method UI logic, 3DS handling) at the cost of less brand customization. Phase 1+ can add Payment Element (embedded UI in your own app) for apps that need the customization.

## Options considered

### Currency: EUR-only vs multi-currency from day one — chose multi-currency

EUR-only is simpler but forces a migration the day a US customer asks to be billed in USD. Given the user's "global from the start" answer, building the multi-Price catalog from day one is cheap (a few fields) and avoids any future migration of historical Subscription records to new Prices.

### Tax: Stripe Tax vs manual vs external — chose Stripe Tax

Manual rates put the legal exposure of reverse-charge mistakes on us. External invoicing (sevDesk etc.) is appropriate later when revenue justifies a dedicated tax-advisor workflow, but adds two-system complexity now. Stripe Tax's 0.5% is cheap insurance and removes whole categories of tax bugs from our code.

Future migration to external invoicing is not blocked — the lib's `Invoices` package abstracts the "create + send invoice" operation behind an interface; an alternative implementation could delegate to a different invoicing system. Designed in, not implemented for phase 0.

### Invoice numbering: trust Stripe vs own — chose trust Stripe, override mechanism designed

Owning numbering is more compliant but adds a critical-path repo (invoice-number sequence) that must be transactional, ordered, and recoverable. The gap risk with Stripe is small and well-documented in tax-advisor practice. The override path is preserved without cost so switching later is trivial.

### Payment methods: cards only vs full suite — chose full suite

Cards only would miss the EU B2B SEPA preference (significantly cheaper for recurring) and the Apple/Google Pay friction reduction (free, just enable). Bank transfer for invoice-style payments is critical for higher-value B2B that won't put €5k on a card. Configuration cost is near zero (Stripe Checkout enables them with one config block).

### Checkout: hosted Stripe Checkout vs embedded Payment Element — chose hosted for phase 0

Hosted Checkout is one API call to create a session, redirect the customer, then receive a webhook on success/failure. Payment Element requires building (or maintaining) the payment UI in each app, handling 3DS in-flow, and a wider surface area for the lib to wrap. Hosted is the right phase-0 default; Payment Element can be added when an app actually needs the embedded experience.

## Consequences

### Positive

- Tax compliance is delegated to Stripe — the lib has near-zero tax logic, near-zero legal exposure.
- VAT ID validation against VIES happens automatically; no VIES integration to build, maintain, or test.
- Multi-currency works on day one without schema changes when expanding to new markets — just add Prices.
- Payment-method coverage is broad without code burden; Stripe Checkout handles all four methods uniformly.
- Invoice compliance "good enough for Austrian B2B" with documented audit-log support for any Finanzamt queries.

### Negative / accepted risks

- **Ongoing cost:** Stripe Tax at 0.5% per transaction. On €1M ARR, ~€5,000/year. Acceptable for the compliance offload.
- **FX cost:** 1% Stripe FX fee on non-EUR settlement to EUR. Acceptable; alternative is multi-currency bank accounts which add operational complexity.
- **Invoice number gaps possible:** mitigated by audit-log helper; switchable to self-managed if Finanzamt ever pushes back.
- **Hosted Checkout limits branding:** acceptable for phase 0; embed-able later.
- **Stripe Tax has product-type categorization rules** (digital service vs SaaS vs physical product) that the catalog must declare. Lib's `Product` type includes a `TaxCategory` field that maps to Stripe's `tax_code`. Apps must set this correctly; lib provides constants for common categories (`TaxCategoryDigitalService`, `TaxCategorySaaS`, etc.).

### Lib API implications

- `Catalog.Product` includes `TaxCategory` (required) and supports multi-`Price` per Product.
- `Checkout.CreateSession` defaults `automatic_tax: true`, `tax_id_collection: true`, `billing_address_collection: 'required'`, and enables payment methods appropriate to the intent (one-time vs subscription vs invoice).
- `Invoices.ExportAuditLog(period)` ships in phase 0 even if invoices themselves are phase 6 — having the audit-log capability from day one prevents scrambling at the first audit request.
- New sub-package `connector/payments` defines payment-method intent presets so apps don't have to think about which methods to enable per use case.

## Out of scope (defer to other ADRs / design docs)

- Invoice flow for net-30 B2B → the relevant package GoDoc (phase 6).
- How catalog sync handles currency additions/removals → the relevant package GoDoc.
- US sales-tax nexus tracking and registration management → out of scope; Stripe Tax does the calculation, registration is a business operation, not a lib concern.
